## A. Executive summary
D-VIEW is an Astro 7 + React 19 + Tailwind 4 static website advertising invisible-grill enquiries in Andhra Pradesh. Source inspection confirmed actionable issues involving customer-information disclosure in an external QR-image URL, misleading WhatsApp completion messaging, a nonfunctional “Connect with Google” verification control, preselected consent and mislinked privacy notice, repeated city alias pages with conflicting canonical signals, a sitemap containing duplicate variants, and invalid footer anchors.

These are confirmed **source-code defects**. They do **not** establish the account-specific cause of Google Ads “Eligible (limited)”. The site also contains safety, warranty, certification, installation, response-time and customer-count claims that require evidence and owner confirmation before alteration or further publication.

## B. Investigation scope and initial baseline
- Repository source: `src/layouts/Layout.astro`; route templates in `src/pages`; React enquiry and dashboard components; `src/data/locations.ts`, `src/data/citiesData.ts`, `src/data/corridors.ts` by inventory; `public/robots.txt`; `public/sitemap.xml`; dependency configuration and CSS.
- 480 repository files inventoried from the Git tree (including media); the sum of tracked file sizes is approximately 317 MB. This is **not** page-transfer size.
- Public route templates: eight principal pages (`/`, about, contact, privacy, solutions, projects, locations, HTML sitemap) and three templates that each generate eleven city/alias variants: 41 static route candidates by source mapping, not verified live URLs.
- Baseline XML sitemap: 39 URL entries, many redundant alias and location-template variants.
- Static scan: 106 distinct referenced image paths across seven inspected major components/data files; all 106 exist in the Git tree. This does not test HTTP retrieval or rendered image quality.
- 84 groups of Git-tracked image paths share identical blob hashes (some across extensions). This is an asset-maintenance opportunity, not proof of poor Core Web Vitals.
- The direct live website and `robots.txt`/`sitemap.xml` requests were inaccessible in the available browser; the container had no DNS/network access. **No production HTTP or browser behavior was verified**, including Google AdsBot access or redirect chain.
- Google Ads and Google Search Console account access was unavailable. No account findings, approval status, indexing status or Google Ads policy decision are inferred.

### Claims requiring source documents
1. **Safety:** “100% fall protection”, “unbreakable”, “400kg/strand”, “impregnable”, toddler safety and fire escape; request an installation-specific engineering report rather than equating strand breaking load with installed-system safety.
2. **Materials/testing:** SS-316 metallurgy, specific molybdenum percentage, 6063-T6 track material, anchor brands and ASTM B117 tests; request supplier specifications, test reports and applicability to actual materials.
3. **Warranty:** signed written terms, exclusions, duration and proof of issuer. Resolve the 5–10-year versus 10-year discrepancy.
4. **Commercial evidence:** 850+ installations, project photos, customer examples, installer certification, same-day or 2-hour promises, and actual service readiness in each of seven cities. No independent substantiation was available.

Read-only account investigation needed:
1. In Google Ads, identify whether the label belongs to **Campaign, Ad group, Ads, Assets or Keywords**.
2. Open the status explanation on the affected item, and go to **Tools → Troubleshooting → Policy manager** where applicable.
3. Record the exact policy name, screenshot with IDs redacted, final URL, tracking template/expanded URL, any verification deadline and affected ad.
4. If Google reports a destination issue, retest that exact expanded URL on mobile/desktop and as AdsBot, including HTTPS/www redirects and relevant robots rules. Make no ad-budget/bid or policy appeal change without explicit authorization.
